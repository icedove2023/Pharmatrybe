# 4. R7A-1 — Outbox Schema

## 4.1 Purpose

The transactional outbox stores durable delivery work generated by a successfully committed invitation transaction.

The outbox represents a request to perform an external delivery operation.

It does not represent the delivery result itself.

---

## 4.2 Required Table

The implementation shall introduce:

```text
invitation_delivery_outbox
````

The table must be tenant-associated through the invitation.

---

## 4.3 Required Fields

The table shall contain the following logical fields:

| Field                   | Requirement                                    |
| ----------------------- | ---------------------------------------------- |
| `id`                    | UUID primary key                               |
| `hospital_id`           | UUID, NOT NULL, references hospital            |
| `invitation_id`         | UUID, NOT NULL, references hospital invitation |
| `idempotency_key`       | TEXT, NOT NULL, UNIQUE                         |
| `delivery_type`         | TEXT, NOT NULL                                 |
| `recipient_email`       | TEXT, NOT NULL                                 |
| `payload`               | JSONB, NOT NULL                                |
| `status`                | TEXT, NOT NULL                                 |
| `attempt_count`         | INTEGER, NOT NULL, default `0`                 |
| `available_at`          | TIMESTAMPTZ, NOT NULL                          |
| `processing_started_at` | TIMESTAMPTZ, nullable                          |
| `last_attempt_at`       | TIMESTAMPTZ, nullable                          |
| `last_error_code`       | TEXT, nullable                                 |
| `last_error_message`    | TEXT, nullable                                 |
| `completed_at`          | TIMESTAMPTZ, nullable                          |
| `created_at`            | TIMESTAMPTZ, NOT NULL                          |
| `updated_at`            | TIMESTAMPTZ, NOT NULL                          |

---

## 4.4 Foreign Keys

`hospital_id` shall reference the hospital table.

`invitation_id` shall reference the invitation table.

The implementation must preserve referential integrity.

---

## 4.5 Raw Token Prohibition

The outbox payload MUST NOT contain the raw invitation token.

The following are prohibited:

```text
raw invitation token
password
JWT
access token
refresh token
secret
private key
authentication credential
```

The outbox may contain only information required to reconstruct the invitation URL through the approved invitation-link mechanism defined in R7A-10.

---

# 5. R7A-2 — Outbox Status Lifecycle

The outbox status is a controlled lifecycle.

The canonical states are:

```text
PENDING
PROCESSING
SENT
FAILED
```

---

## 5.1 `PENDING`

Initial state.

The record exists and has not yet been claimed by a delivery worker.

---

## 5.2 `PROCESSING`

A worker has atomically claimed the record for delivery.

Only one worker may own a delivery attempt at a time.

---

## 5.3 `SENT`

The external delivery provider has accepted the delivery request successfully.

`SENT` is terminal.

A `SENT` record must not be retried.

---

## 5.4 `FAILED`

The delivery operation has reached a terminal non-retryable condition or exhausted the approved retry budget.

`FAILED` is terminal.

---

## 5.5 Valid Transitions

The only permitted transitions are:

```text
PENDING → PROCESSING
PROCESSING → SENT
PROCESSING → PENDING
PROCESSING → FAILED
```

No other status transitions are permitted.

In particular:

```text
SENT → PROCESSING
SENT → PENDING
FAILED → PROCESSING
FAILED → PENDING
```

are prohibited.

---

# 6. R7A-3 — Attempt and Retry Semantics

## 6.1 Attempt Counter

`attempt_count` represents the number of delivery attempts actually started.

Initial value:

```text
0
```

When a worker claims a record for delivery:

```text
attempt_count = attempt_count + 1
```

The increment occurs before the external delivery call.

---

## 6.2 Maximum Attempts

The maximum number of delivery attempts is:

```text
3
```

Therefore:

```text
attempt_count ∈ {0,1,2,3}
```

No fourth delivery attempt may occur.

---

## 6.3 Retryable Failure

If the provider failure is classified as retryable and:

```text
attempt_count < 3
```

the worker shall return the record to:

```text
PENDING
```

and assign a future `available_at`.

---

## 6.4 Retry Schedule

The retry schedule shall use bounded exponential backoff:

```text
Attempt 1 failure → retry after 1 minute
Attempt 2 failure → retry after 5 minutes
Attempt 3 failure → terminal FAILED
```

No retry occurs after the third failed attempt.

---

## 6.5 Delivery Failure Does Not Roll Back Identity

Once the invitation transaction has committed:

* hospital state remains committed;
* invitation state remains committed;
* membership state remains committed where applicable;
* outbox state remains committed.

External delivery failure must never roll back committed database state.

---

# 7. R7A-4 — Idempotency

## 7.1 Idempotency Key

Every invitation delivery outbox record shall contain:

```text
idempotency_key
```

The value shall uniquely identify the delivery operation for an invitation.

The canonical construction is:

```text
invitation:{invitation_id}:initial
```

---

## 7.2 Database Enforcement

`idempotency_key` shall have a unique database constraint.

Therefore, a single invitation cannot create multiple initial delivery jobs.

---

## 7.3 Duplicate Worker Protection

Workers must claim work atomically.

A worker must not process an outbox row already claimed by another active worker.

The implementation shall use database transaction semantics appropriate to PostgreSQL, such as row locking / atomic claim behavior.

---

## 7.4 Reprocessing

If a worker crashes after claiming a record but before completing delivery, R7A-7 governs recovery.

A recovered record must retain its existing idempotency key.

A recovery operation must not create a second outbox record.

---

# 8. R7A-5 — Delivery Abstraction Interface

External delivery shall be isolated behind a provider-neutral backend abstraction.

The application must not directly couple invitation creation to a specific email vendor.

---

## 8.1 Logical Interface

The delivery abstraction shall expose the equivalent of:

```python
send_invitation(
    recipient_email: str,
    invitation_url: str,
    invitation_id: UUID,
    idempotency_key: str,
) -> DeliveryResult
```

Exact Python naming may follow existing project conventions, but the contract must remain equivalent.

---

## 8.2 Delivery Result

The abstraction shall return a structured result containing:

```text
success
failure classification
provider/reference identifier when available
safe diagnostic information
```

It must not expose secrets or raw invitation tokens.

---

## 8.3 Provider Independence

The invitation service must depend on the abstraction rather than a concrete provider.

A future provider may therefore be substituted without changing:

* invitation creation;
* invitation acceptance;
* membership logic;
* RBAC;
* tenant resolution.

---

# 9. R7A-6 — Worker Ownership

The delivery worker is responsible only for delivery processing.

The worker owns:

1. Selecting eligible outbox records.
2. Atomically claiming them.
3. Incrementing the attempt count.
4. Constructing the invitation URL using the approved mechanism.
5. Calling the delivery abstraction.
6. Recording the result.
7. Scheduling approved retries.
8. Marking terminal failure.

The worker does NOT:

* create memberships;
* assign roles;
* authorize users;
* resolve authorization from client input;
* modify invitation ownership;
* accept invitations;
* bypass RBAC;
* modify clinical data.

---

# 10. Worker Concurrency

Multiple workers may operate concurrently.

Each worker must claim a record atomically.

The implementation must prevent two workers from simultaneously processing the same outbox row.

PostgreSQL locking/claim semantics shall be used rather than an application-only in-memory lock.

---

# 11. R7A-7 — `PROCESSING` Recovery

A `PROCESSING` record may become orphaned if a worker crashes.

The system shall therefore support recovery.

---

## 11.1 Stale Definition

A `PROCESSING` record is stale when:

```text
processing_started_at < current_timestamp - 15 minutes
```

---

## 11.2 Recovery Action

A stale `PROCESSING` record shall be returned to:

```text
PENDING
```

provided:

```text
attempt_count < 3
```

Its `available_at` shall be set to the current time.

---

## 11.3 Recovery After Maximum Attempts

If:

```text
attempt_count >= 3
```

the stale record shall transition to:

```text
FAILED
```

and no further delivery attempt shall occur.

---

## 11.4 Recovery Safety

Recovery must use an atomic database operation.

A live worker must not have its active record incorrectly reclaimed.

The stale threshold exists specifically to provide a bounded crash-recovery window.

---

# 12. R7A-8 — Failure Classification

Delivery failures shall be classified into:

```text
RETRYABLE
NON_RETRYABLE
```

---

## 12.1 Retryable Failures

Retryable failures include temporary infrastructure/provider conditions such as:

* provider unavailable;
* network timeout;
* transient connection failure;
* temporary provider error;
* temporary rate limiting.

These failures may return the record to `PENDING` when attempts remain.

---

## 12.2 Non-Retryable Failures

Non-retryable failures include conditions such as:

* invalid recipient address;
* permanently rejected recipient;
* malformed delivery request;
* unsupported delivery operation;
* permanent provider rejection.

These failures transition directly to:

```text
FAILED
```

---

## 12.3 Unknown Failure

An unknown provider failure must be treated conservatively as:

```text
RETRYABLE
```

until the retry budget is exhausted.

After the third attempt:

```text
FAILED
```

---

## 12.4 Error Storage

`last_error_code` may contain a stable machine-readable classification.

`last_error_message` must contain only sanitized diagnostic information.

The following must never be persisted:

```text
raw token
JWT
password
API secret
provider credential
authorization header
refresh token
```

---

# 13. R7A-9 — Outbox Security and RLS

The outbox is backend infrastructure.

It is not a frontend-readable application resource.

---

## 13.1 Client Access

Authenticated application clients must not directly:

```text
SELECT
INSERT
UPDATE
DELETE
```

outbox records.

---

## 13.2 Backend Access

The backend/service role may access the outbox for:

* insertion as part of invitation creation;
* worker claim;
* delivery state update;
* retry;
* recovery.

---

## 13.3 Tenant Isolation

Every outbox row contains:

```text
hospital_id
```

and is associated with its invitation.

Application-level tenant resolution must remain authoritative for invitation creation.

The worker must not accept a client-provided hospital identifier.

---

## 13.4 RLS

The implementation shall ensure that outbox data cannot become a cross-tenant client-readable surface.

If RLS is enabled for the table, policies shall deny ordinary client access and permit only the approved backend/service execution path.

The implementation must not weaken existing tenant RLS to accommodate the outbox.

---

# 14. R7A-10 — Invitation-Link Construction

The raw invitation token shall never be stored in:

* database columns;
* outbox payload;
* logs;
* audit records;
* analytics;
* error messages.

---

## 14.1 Token Lifetime

The invitation token is generated at invitation creation time.

The token is returned only through the approved invitation-delivery pathway.

The raw token must not be persisted.

---

## 14.2 Outbox Payload

The outbox shall persist sufficient non-secret information to identify the invitation delivery operation.

The payload must NOT contain the raw token.

---

## 14.3 Link Construction

The invitation link shall be constructed from:

```text
approved frontend invitation route
+
opaque invitation token supplied only to the delivery operation
```

The delivery worker may obtain the token required for the outbound message only through an approved secure mechanism.

It must never reconstruct a token from its hash.

A cryptographic hash is one-way and therefore cannot be used to recover the original token.

---

## 14.4 Required Secure Token Handling

Because the raw token cannot be recovered from its hash, the implementation shall use the following model:

1. Generate the raw token.
2. Hash the token for persistent invitation verification.
3. Place the raw token only in the immediate delivery job payload/in-memory delivery boundary.
4. Persist only the hashed token and non-secret delivery metadata.
5. Ensure the raw token is never written to database storage, logs, audit records, or persistent outbox JSONB.
6. If asynchronous delivery requires the token after the transaction commits, the implementation must use a dedicated short-lived secure delivery mechanism rather than persisting the raw token in the transactional outbox.

The delivery mechanism must not introduce a second long-lived token store.

---

# 15. Important Constraint on Asynchronous Delivery

The transactional outbox exists to guarantee durable delivery intent.

It must not become a mechanism for persisting invitation secrets.

Therefore:

```text
Database transaction
    ↓
Invitation + identity state
    ↓
Outbox delivery intent
    ↓
External delivery
```

must preserve the separation between:

```text
durable delivery metadata
```

and:

```text
secret invitation credential
```

# 16. Invitation Transaction Boundary

Invitation creation shall remain a single database transaction for all database state created by the invitation operation.

The transaction includes:

* invitation creation;
* required invitation metadata;
* delivery outbox creation.

The external delivery operation does NOT occur inside this transaction.

# 17. Commit Ordering

The required sequence is:

```text
Authenticate caller
        ↓
Authorize professionals:invite
        ↓
Resolve authenticated hospital
        ↓
Validate target role
        ↓
Generate invitation token
        ↓
Persist invitation using token hash
        ↓

        ↓
COMMIT
        ↓
Asynchronous delivery worker
        ↓
External provider
```

If any database operation before commit fails:

```text
ROLLBACK
```

No invitation delivery work shall survive the rollback.

# 18. Delivery Failure Semantics

invitation remains valid/pending

The system must not delete or invalidate the invitation merely because email delivery failed.

Retry follows R7A-3 and R7A-8.

# 31. Final Architectural Statement

R7A establishes the transactional outbox as the durable boundary between committed invitation state and asynchronous external delivery.

The database transaction guarantees that an invitation and its delivery intent either both exist or neither exists.

The delivery worker is responsible only for asynchronous delivery.

The worker uses bounded retries, explicit failure classification, idempotent processing, and crash recovery.

Invitation tokens remain confidential and are never persisted in the outbox.

External delivery failure cannot corrupt or roll back committed identity state.

The outbox is an internal backend mechanism and does not become a client-facing authorization surface.

No further architectural interpretation is required for the ten R7A decisions defined above.
