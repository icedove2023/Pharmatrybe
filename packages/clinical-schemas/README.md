# Overview

The **Clinical Schemas Package** defines the official data contracts used throughout the PharmaTrybe platform.

Every service within PharmaTrybe communicates using these shared schemas.

No service is permitted to define its own independent payload structure.

These schemas provide a common language between:

- Next.js Frontend
- FastAPI Backend
- SOAR/GSK AI Engine
- ARMD AI Engine
- WHO Knowledge Engine
- Clinical Decision Engine
- Explainability Engine
- Supabase Platform Services

This approach guarantees consistency, interoperability, transparency, auditability, and long-term maintainability.

---

# Design Philosophy

The schema architecture follows several core principles.

## Single Source of Truth

Each clinical object is defined once.

Every service consumes and produces the same object definitions.

---

## Service Independence

Each service remains internally independent.

Services communicate only through shared contracts.

Internal implementation details are never exposed.

---

## Clinical Safety

Schemas are designed around clinical workflows rather than software convenience.

Clinical meaning always takes priority over implementation details.

---

## Explainability

Every schema contains sufficient information to support transparent clinical reasoning and audit.

No recommendation should exist without traceable supporting evidence.

---

## Extensibility

Future AI models must integrate using these schemas without requiring architectural redesign.

Examples include:

- Sepsis AI
- Urinary Tract Infection AI
- Tuberculosis AI
- Surgical Prophylaxis AI
- Neonatal Infection AI

# Schema Catalogue

The following documents form the official PharmaTrybe clinical contract.

| Schema | Purpose |
|---------|---------|
| Clinical Case | Canonical patient input shared by all services |
| Respiratory Schema | Output contract for the SOAR/GSK model |
| ARMD Schema | Output contract for the ARMD resistance prediction model |
| WHO Schema | Knowledge response generated from the WHO evidence database |
| Recommendation Schema | Unified recommendation generated by the Clinical Decision Engine |
| Explainability Schema | Structured clinician-facing explanation |
| Audit Schema | Complete traceability and governance record |
| Enums | Standard platform enumerations |
| Glossary | Official definitions of all clinical terminology |

# Service Responsibilities

## SOAR/GSK

Responsible for:

- Respiratory pathogen prediction
- Respiratory susceptibility prediction
- Confidence estimation

Not responsible for:

- Drug selection
- Stewardship decisions
- WHO interpretation

---

## ARMD

Responsible for:

- Hospital resistance prediction
- Prior antibiotic exposure analysis
- Previous organism analysis
- Risk estimation

Not responsible for:

- Antibiotic recommendation
- WHO interpretation
- Clinical decision making

---

## WHO Knowledge Engine

Responsible for:

- WHO AWaRe classifications
- Clinical guidelines
- Drug information
- Stewardship recommendations
- Monitoring guidance
- Follow-up guidance
- Referral guidance

Contains no machine learning.

---

## Clinical Decision Engine

Responsible for combining:

- SOAR evidence
- ARMD evidence
- WHO guidance
- Clinical rules

into one recommendation.

---

## Explainability Engine

Responsible for translating technical outputs into clinician-readable explanations.

# Versioning Policy

Every schema includes:

- Schema Version
- Contract Version
- Timestamp
- Trace Identifier

Breaking schema changes require a new major version.

Minor additions must remain backward compatible.

# Governance

The Clinical Schemas Package is governed by the PharmaTrybe Architecture.

Any modification to these schemas must satisfy the following requirements:

- Preserve backward compatibility whenever possible.
- Maintain alignment with the PharmaTrybe Platform Architecture.
- Protect clinical safety.
- Preserve explainability.
- Maintain auditability.
- Ensure interoperability across all services.

# Relationship to the WHO Database

The WHO Knowledge Engine may retrieve information from multiple internal database tables, including:

- Diseases
- Pathogens
- Drugs
- Recommendations
- Recommendation–Pathogen mappings
- Diagnostics
- Monitoring
- Follow-up
- Stewardship
- Referral
- Evidence
- Metadata

These internal database structures are **implementation details**.

Other PharmaTrybe services **must never communicate directly with database tables**.

Instead, they consume the standardized WHO Schema defined within this package.
